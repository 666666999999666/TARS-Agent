# 三个可重复演示任务

使用 `tars chat` 连续对话、`tars run --goal "任务"` 执行一次性任务，或使用 `tars-tui`。每轮准备新的工作区、随机标记和独立会话，不使用真实用户文件；启动和恢复方法见[运行说明](../../RUNBOOK.md)。模型调用和资源操作按当次授权执行，历史文档不能代替本次确认。

## 1. 文件工作流

在新工作区准备包含随机标记的 `源数据.txt`，向 chat 或 TUI 提交：

> 请列出当前工作区，读取源数据.txt，把其中的标记写入报告.md，读回核对，并保存为本会话笔记。只操作当前工作区。

在需要时批准本次操作。打开实际报告和会话笔记，核对标记；再检查持久工具记录和 Run 终态。模型说“已完成”不能代替文件和记录。

goal 使用相同目标作为 `--goal` 参数，在交互终端中审批。正常流程的退出码应为 `0`；如果发生工具失败，即使模型随后补救成功，goal 也应返回 `1`。检查完后确认 Core 仍可查询。

## 2. 权限工作流

先要求读取标记并写入 `被拒绝.txt`，在 CLI 审批提示中输入 `n`，或在 TUI 弹窗中拒绝。确认文件没有出现，模型明确说明操作被拒绝。goal 应返回 `1`；chat 应保留输入提示，让用户继续下一轮。

下一轮明确要求改为写入 `替代结果.txt` 并读回，单独批准这个新请求。核对新文件、实际工具调用及新的审批记录；旧批准不能覆盖改变后的参数，也不能扩大工作区或自动转为宿主执行。

## 3. 会话工作流

在 chat 中让 Agent 读取并记住随机代号，连续追问几轮，然后用 EOF 退出；再以 `tars chat --resume <session_id>` 恢复，检查能否继续使用记忆，Core 不应随客户端退出。

TUI 另行验证：保存笔记，在空闲时执行 `/compact`，按 Ctrl+Q 退出，再通过 `tars-tui --resume <session_id>` 恢复。不要把 CLI 的 EOF 与 TUI 的 Ctrl+Q 混为同一次界面验收。

在独立验收环境中重启本次 Core 后再次恢复会话。随后运行一个有明确开始标记和延迟副作用的测试任务，CLI 用 Ctrl+C、TUI 用 Ctrl+X 取消，确认延迟文件没有产生；chat/TUI 再完成一个新的合法任务。goal 取消后应返回 `130`。只停止本次测试 Core，不接管原 daemon。

核对恢复游标、最终文件和 SQLite：没有自动重复提交最后输入；取消消息没有进入成功上下文；终态 Run 所属的工具记录不再是 `queued` 或 `running`。

## 重复运行与结果

核心文件、权限、会话工作流按原验收安排连续三轮验证。同类某轮失败后先保留证据并查明原因，不用一次偶然成功代替稳定复测；已验证且未受修改影响的成果保留。

[验收脚本说明](REAL_WORKFLOWS.md)区分真实 CLI 驱动和底层 RPC 工作流。RPC 脚本保留三类各三轮，逐 Run 检查 `terminal_tool_check`；CLI 还要实际运行两种命令、审批、取消、EOF、恢复及退出码，TUI 还要实际操作界面。三者不能互相冒充。

当前演示和验收结果统一见[验证摘要](VERIFICATION_SUMMARY.md)，不在这里复制阶段数字。
